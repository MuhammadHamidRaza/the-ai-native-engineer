Before writing a line of orchestration code, name the shape. Topology is the highest-leverage decision in a multi-agent system: get it right and failure modes are obvious; get it wrong and no amount of prompt tuning recovers coherence.

## The Topology Taxonomy at a Glance

| Topology | Shape | Communication | ShopCore example |
| :-- | :-- | :-- | :-- |
| **Supervisor** | One orchestrator delegates to specialists, synthesizes | Star — hub routes tasks, workers never talk directly | Postmaster as supervisor: refund specialist, shipping specialist, policy specialist |
| **Router** | Classifier picks one specialist; done | Classify-once, then hand off | Inbound ticket → billing-agent vs support-agent vs escalation |
| **Pipeline** | Fixed linear stages with typed handoffs | A → B → C | Research Brief: retrieve → draft → critique → publish |
| **Map-Reduce** | Parallel fan-out, then merge/reduce | Workers independent; reducer merges | Competitor scan: 6 agents in parallel → synthesis |
| **Swarm** | Peer agents cooperate via shared workspace, no boss | Many-to-many via blackboard | Experimental; rarely justified — see honest guidance |

Selection is a function of **dependency structure**: independent subtasks → map-reduce; sequential dependency → pipeline; routing by classification → router; judgment-heavy coordination → supervisor; nothing else fits → question whether you need multi-agent at all.

## Why Contracts Come With Topologies

Every topology is only as reliable as its handoff format. A supervisor that delegates with prose ("handle the refund stuff") instead of a typed envelope (`{kind:"refund_review", orderId, ...}`) fails silently at 2 a.m. Topology and contracts are one design decision, taught together here.
