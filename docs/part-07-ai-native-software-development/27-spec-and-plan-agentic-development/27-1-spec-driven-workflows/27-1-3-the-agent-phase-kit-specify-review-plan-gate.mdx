You have seen specs (27.1.1) and tasks (27.1.2). What you have not seen is a full closed loop — from idea to merged PR across many sessions — that does not depend on the agent's memory. This lesson dissects one concrete, open-source attempt: the **Agent Phase Kit**. Treat it as a field study, not a religion. Everything here is reproducible, and most of it is negotiable.

## 1. The Case Study: ai-agent-phases

Verified November 2026: `github.com/MuhammadHamidRaza/ai-agent-phases` is reachable and public. MIT license. Branded as "Agent Phase Kit" — a phase-by-phase, spec-driven setup for AI coding agents. It is deliberately **not a framework or CLI**: it is four Markdown files plus two paste-in prompt templates, designed to work with Claude Code, OpenCode, Codex CLI, Gemini CLI and Cursor. Small project (a handful of assets and one README at time of writing), which matters: the whole idea is that process lives in your repo, not in a tool you install.

The four files it prescribes:

| File | Role | Read by agent |
| :-- | :-- | :-- |
| `AGENTS.md` | The rulebook — non-negotiables, session protocol, which tool reads what | First, every session |
| `PHASES.md` | The plan — phases with at most 5 tasks, a Goal, a Build list, a Not-yet list, and a Gate | The current phase section only |
| `PROGRESS.md` | Live status — phase table, blockers, session log, and a `RESUME HERE` block | Every session, always |
| `IDEAS.md` | Parking lot — one row per stray idea; never actioned mid-phase | Only when asked, or between phases |

Bridge files matter: OpenCode, Codex CLI and Cursor read `AGENTS.md` natively; Claude Code reads `CLAUDE.md` (kit says create it containing one line, `@AGENTS.md`); Gemini CLI reads `GEMINI.md` (one line, `@./AGENTS.md`, or set its `context.fileName` to include AGENTS.md). Never rename the master file to suit one tool or the others go blind.

## 2. The Workflow and Why It Exists

The loop per phase:

```text
Specify --> Review --> Plan --> Review --> Tasks --> Review --> Implement --> Gate --> Commit --> New session
   (you)     (you check)   (agent)   (you)    (agent)   (you)   (agent)   (real cmd output)  (you)
```

Every arrow points at a human checkpoint except Implement. The rules that make it work:

- **One phase = one spec = one or two sessions.** Max 5 tasks per phase. If describing the phase needs the word "and", split it.
- **Rule of 3.** If a gate fails 3 times, the agent stops, marks the phase blocked, and asks you. No spiraling.
- **Fresh session per phase.** `/clear` in Claude Code, `/new` in OpenCode (both verified, Nov 2026). Compact only mid-phase, at roughly 60-70 percent context, e.g. `/compact keep the current task, decisions, changed files, open bugs, next step` — and only if the tool honors instructions; otherwise pin the rule in AGENTS.md.
- **The gate is real.** `npm run build -> exits 0`, not "the agent said it builds". The kit's own README tells the story: one phase had 398 passing unit tests, yet the real gate caught a database migration that silently did nothing and a CLI flag the tool had removed. Unit tests lied; the gate did not.
- **Memory lives in files.** The chat is disposable; the repo is permanent.

Resume protocol for any fresh session: read `AGENTS.md`, read `PROGRESS.md`'s `RESUME HERE` block, read only the named phase section of `PHASES.md`, do the next task, run the gate, update `PROGRESS.md`, commit, stop.

This directly attacks the two failure modes that kill long agent projects: **context rot** (the conversation degrades as it fills; early decisions silently drop out) and **loader drift** (the agent re-derives stale assumptions from a huge window instead of reading a 30-line resume block). Fresh sessions with file-backed memory are cheap; long drifted sessions are not.

## 3. Worked Example: Abandoned Cart, Kit Edition

Continuing our ShopCore feature. `AGENTS.md` excerpt:

```markdown
# AGENTS.md (excerpt)
## Non-negotiables
1. One phase at a time. No work outside the current phase section of PHASES.md.
2. Gates require real command output pasted into PROGRESS.md. "Done" without output is not done.
3. Smallest change that passes the gate. No refactors "while you are here".
4. New ideas go to IDEAS.md with one line. Never act on them mid-phase.
5. No secrets in any file. Ask before installing anything.
## Session protocol
Read PROGRESS.md RESUME HERE -> read ONLY that phase in PHASES.md -> next task -> run gate -> update RESUME HERE -> commit -> stop.
```

`PHASES.md` excerpt:

```markdown
## Phase 3 - Abandoned cart reminder email
Goal: One reminder email per logged-in abandoned cart, >= 4h old, audited.
Build: src/jobs/abandoned-cart-scan.js, cart_reminders table, one Postmark template.
Not-yet (do NOT build): guest carts, coupons, SMS, template editor, marketing pipeline.
Tasks (max 5):
 1. Migration 2026-11-20 up/down for cart_reminders
 2. findUnrecoveredCartsOlderThan(hours, limit) + unit tests
 3. Job sends exactly one email per eligible cart
 4. Skip/recovered logic + mailer-failure writes zero rows
 5. Cron registration + ABANDONED_CART_EMAIL flag + gate
Gate:
  npm run migrate && npm run migrate -- --down && npm run migrate  -> exits 0
  npm test -- --grep abandoned-cart                                -> 6+ passing
  npm run lint                                                     -> exits 0
  node src/jobs/abandoned-cart-scan.js --once (seeded 5h-old cart) -> 1 test email, 1 row in cart_reminders
```

## 4. Dead Phase Recovery and When to Halt

A phase is "dead" when three gate attempts have failed or the agent loops. Recovery ladder:

1. **Re-scope, not re-prompt.** The phase was almost certainly too big. Split it; the Not-yet list absorbs the excess.
2. **Re-anchor the context.** Fresh session, resume line from RESUME HERE, nothing else. Do not "fix" by adding more chat history.
3. **Bisect the gate.** Which single command fails? Run it by hand. If it fails identically, the plan (not the model) is wrong — go back to Plan review.
4. **Escalate to a human decision.** Blocked phases get an options list in IDEAS.md (or the blockers table) and a stop. The kit's own rule: after 3 failures, stop and ask; do not glue complexity onto a failing gate.

Halt immediately (phase or project) when: the gate failure looks like data loss or security exposure; the agent proposes editing the gate to pass; the agent proposes deleting or weakening a test; requirements are discovered to be mutually exclusive; or you cannot state the undo path. Those are human calls, not agent calls.

## 5. Honest Strengths, Weaknesses, and Fixes

**Strengths.** Persistent file-backed memory across sessions; adversarial human-in-the-loop review at every step; gates with real output end the "agent said done" problem; tiny phases make failure cheap; the Not-yet list and IDEAS.md genuinely reduce scope creep; works with any tool that reads Markdown.

**Weaknesses and failure modes.**

- *Overhead on small work.* Ceremony eats hours on a one-file bugfix. The truthful threshold: if a gate takes longer to write than the fix takes to code, skip the kit.
- *False-comfort compliance.* Agents (and humans!) can paste stale gate output, rerun until flake passes, or mark a task done because tests exist. Gates verify what you ask, not what you meant; weak gates produce compliant garbage.
- *Review-as-rubber-stamp.* Six review checkpoints a day train tired humans to click "yes". The skill is in reviewing differently each step (spec logic vs plan soundness vs output correctness), not equally.
- *PHASES.md bloat.* Once it grows past a screen, agents start skimming and "forgetting" constraints — the context rot returns through the front door. Keep phases lean; past phases are history, summarized, not re-read.
- *Single-operator bias.* Built by one author for their workflow. Your team may need roles, ownership, and sign-off the kit does not model.

**Improvements that work.** Add scope fences (explicit directories the agent may never touch), deletion discipline (each phase closes by deleting dead code it found), and an explicit "definition of phase done" signed by a human in PROGRESS.md. Rotate gate authors (person A writes the gate, person B reviews the output) to kill rubber-stamping.

## 6. Honest Comparison with Spec-Driven Alternatives

- **GitHub Spec Kit** (MIT, ~150k stars, verified Nov 2026; `uv tool install specify-cli`, then `specify init`): the heavyweight. Current SDD flow is `/speckit-constitution` -> `/speckit-specify` -> `/speckit-plan` -> `/speckit-tasks` -> `/speckit-implement` -> `/speckit-converge` (invocation syntax varies by agent integration; the kit's README uses `/sp.specify`-style names, which may not match your install). Strengths: structured, rich constitution/templates, extension catalog, good for enterprises wanting traceability. Weaknesses: rigid phase gates, heavyweight prompts, Python/uv setup, commands sprawl as extensions multiply. Choose it when the org needs audit trails more than velocity.
- **BMAD Method** (balances analysis/architecture/dev/test roles; stable v6.12 via `npx bmad-method install`, Node 20.12+, Python 3.10+, `uv`; V7 preview alpha in progress as of Nov 2026, skill-based, moving target; MIT, ~55k stars): strength is role-based depth (analyst, architect, PM personas produce sharper upfront artifacts) and "right-sized" planning paths. Weaknesses: install weight, persona roleplay overhead, v7 flux. Choose it for genuinely complex, ambiguous greenfield systems where thinking outruns typing.
- **OpenSpec** (Fission-AI, MIT, ~75k stars, verified Nov 2026; `npm install -g @fission-ai/openspec@latest`, Node 22.20+, `openspec init`): open-source, fluid, brownfield-friendly; changes live in `openspec/changes/<name>/` as proposal + specs + design + tasks; workflow exposed as skills (`/openspec-explore`, `/openspec-propose`, `/openspec-apply-change`, `/openspec-archive-change`; Codex invokes as `$openspec-propose`); v2.0 with "Stores" (beta) for cross-repo planning. Strengths: low ceremony, living specs, great for existing codebases. Weaknesses: fewer built-in gates, discipline is optional, you build your own quality harness.
- **Agent Phase Kit** (this lesson): the lightest of the four — zero install, maximum portability, gates are the whole religion. Strengths: ten-minute setup, works everywhere, transparent. Weaknesses: no tooling safety net, consistency depends on human discipline, thin ecosystem.
- **Plain spec-driven without any kit**: perfectly viable if you already run disciplined code review. Kits encode habits; if your habits are already good, the kit is redundant ceremony.

Pick by constraint, not enthusiasm: org mandates traceability -> Spec Kit; ambiguous large greenfield -> BMAD; brownfield repo, one team -> OpenSpec; solo/small team, mixed tools, want minimal deps -> Agent Phase Kit; disciplined existing process -> keep it.

**Do not use any of this for:** one-line bugfixes, exploratory spikes with unknown shape (timebox instead, delete after), or throwaway prototypes — the gate ceremony will cost more than the prototype, and you will learn nothing about real scope from a fake one.

## 7. Practice

**Guided exercise.** Replicate the kit on a scratch repo: write the four files for a trivial feature (e.g., add a dark-mode toggle). Run one phase with `claude` fully fresh-sessioned. Paste the gate output.

**Independent exercise.** Take your current project and run the kit on one real phase. Log every place the agent went off-script and which of the five weaknesses it maps to.

**Challenge.** Steal the best 20 percent of two different kits for your team (e.g., Phase Kit's RESUME HERE + OpenSpec's change folder). Write a one-page internal README justifying each borrowed piece.

**Assessment checklist**

- [ ] I can recite the four kit files and the nine-step loop without looking.
- [ ] My gates are commands with expected output, never "tests pass" prose.
- [ ] I start a fresh session per phase and use /clear or /new deliberately.
- [ ] I know when to split a phase and when to halt and ask a human.
- [ ] I can name two real weaknesses of the kit and one real alternative for my context.
