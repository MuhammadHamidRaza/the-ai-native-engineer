Instructions tell the model what you want; **examples show it**. Few-shot prompting is the cheapest accuracy lever you own — but it is also the easiest to cargo-cult: wrong count, wrong order, wrong distribution, and you have paid tokens for confident noise. This lesson covers when 0/1/3/5+ examples help, the ordering and label-leakage traps, and the reasoning scaffolds (chain-of-thought and friends) with honest guidance on when they hurt.

## 1. How Many Shots — 0, 1, 3, 5+

| Shots | Use when | Cost |
| :-- | :-- | :-- |
| **0** | Task is common in training data and your contract is explicit; classification with obvious labels; extraction with a strict schema | Cheapest; try this first |
| **1** | The *format* is the hard part — one perfect example pins field order, label spelling, tone | ~1 example of overhead |
| **3** | One example per class for a 3-class task; covering a typical case + one boundary + one "none of the above" | Usually the sweet spot |
| **5+** | Formats are brittle, classes overlap, or you must demonstrate edge-case handling; rarely beyond ~8 — diminishing returns hit fast | Tokens add linearly; noise risk grows |

Rule of thumb: **add examples only after the zero-shot contract fails on real inputs** — and measure with an eval suite (Section 26.2.2), not vibes.

## 2. Ordering Effects — Recency Bias Is Real

Models overweight the last example(s) in the prompt (a recency effect, mirroring the lost-in-the-middle finding in 26.2.1). Consequences:

- If the last three examples are all `approve`, the model leans `approve` — even for a denial.
- If your final example ends with a particular JSON key order, expect that order verbatim.
- Rotating example order between requests in production can change answers for identical inputs. (Mitigate: fix the order, pin the model, eval on every change.)

Practice: audit the **last** example specifically; make it a clean, typical, correctly-labeled case. Never let it be your weirdest edge case — that is how the model learns "everything looks like the weird case."

## 3. Distribution Matching — Examples Are a Dataset

Few-shot examples define the *implied* distribution the model conditions on. If your ShopCore refund classifier sees 80% damaged-item tickets in production, a prompt with 5 textbook "changed my mind" examples teaches the wrong prior. Match the real mix, and deliberately include:

- **Edge cases:** damaged-on-arrival (approve), buyer's-remorse-after-13-days (boundary denial), missing order ID (escalate).
- **The honest "other" path:** at least one example that is none of your classes.
- **Hard negatives:** cases that superficially look approve-able but are not (already refunded; outside window).

A 5-shot prompt with distribution matching beats a 10-shot prompt that is five near-duplicates of the easy case.

## 4. How Labels Leak the Task

Label names are an information channel — sometimes the main one:

- `approve` / `deny` / `escalate` — terse, balanced, leak nothing extra. Good.
- `refund_obviously_fine` / `refund_suspicious` — leak your *conclusions* instead of the boundary; the model keyword-matches "suspicious."
- Inconsistent casing or spelling across examples (`Escalate`, `ESCALATE`, `escalate`) teaches the model that labels are free-text — expect it to invent `escalation`.

Keep labels short, one per line of reasoning, byte-identical everywhere (prompt, eval set, downstream code).

## 5. Reasoning Scaffolds — CoT, Plan-Then-Answer, Self-Consistency

**Chain-of-thought (CoT)** — "Let's think step by step" or an explicit "Reasoning: ... Answer: ..." format (Wei et al., 2022). Elicits intermediate steps before the final answer; strong gains on multi-step arithmetic, logic and planning.

**Plan-then-answer** — force the model to emit a short plan (numbered steps) first, then execute. Cheaper cousin of full CoT; works well for tool use and multi-document synthesis.

**Self-consistency** — sample N reasoning paths at temperature > 0 and majority-vote the final answer (Wang et al., 2022). Buys robustness at N× the token cost; use when errors are expensive and answers are discrete.

**When NOT to use CoT — the honest list:**

- **High-volume classification/extraction.** CoT triples token spend for single-digit-point gains; your 26.2.2 eval will usually say plain few-shot is enough.
- **Reasoning errors surface as wrong answers at scale.** At 30k tickets/month, a 5% reasoning-slip rate is 1,500 silently wrong actions. If you cannot verify each step, do not ask for steps — ask for a label plus confidence, and route low-confidence to a human.
- **Knowledge gaps.** CoT cannot deduce a fact that is not in the prompt or the weights; it will narrate a plausible wrong path beautifully.
- **Latency-critical UX.** Streaming a reasoning monologue before every answer feels slow; reserve CoT for the hard 5%.

## 6. Worked Example — Classifying ShopCore Refund Requests

Task: label an incoming ticket `approve`, `deny`, or `escalate`. Items: 200 historical tickets with human labels (the 26.2.2 eval set).

**Zero-shot:**

```text
System: Classify the ticket as approve, deny or escalate. Reply with only the label.
User: "Hi, my blender arrived with a cracked jug, order #4471, delivered Tuesday..."
```

Typical outcome: solid on obvious cases, weak precisely on the boundary (13-day defective claim, missing order ID).

**5-shot:** add five matched examples spanning approve (damaged, in-window), approve (wrong item), deny (outside 14 days), deny (buyer's remorse, not defective), escalate (missing order ID / threatening chargeback).

A **5-shot** prompt that passes on dev tickets:

```text
System: Classify each ticket. Reply with exactly one word:
approve, deny or escalate.
Examples:
T: "blender arrived with a cracked jug, order #4471" -> approve
T: "received wrong size, want exchange not refund"   -> approve
T: "item fine but changed my mind after 10 days"     -> deny
T: "delivered 20 days ago, screen dead"              -> deny
T: "my order never arrived and I want $9,000"        -> escalate

User: T: "washing machine smells like burning, order #4520"
```

Typical outcome: noticeably fewer boundary errors; near-zero label-format failures.

**CoT-5 (5-shot with "Reasoning:" before "Answer:"):**

```text
Ticket: "blender arrived cracked, order #4471, delivered Tuesday"
Reasoning: Defective on arrival = in scope. 14-day window from delivery:
delivered Tuesday, today is Thursday = in window. Order ID present.
Answer: approve
```

Typical outcome on the same 200 tickets: roughly **0-shot in the low-70s% accuracy, 5-shot in the low-80s, CoT-5 a few points above 5-shot, concentrated on the boundary cases** — at roughly 3–4× the output tokens of plain 5-shot. Treat those numbers as the *shape* teams routinely report, not a promise; your eval set will produce your numbers. (Measure, do not trust. And never let CoT output flow unchecked into the refund tool — see 26.2.3.)

```text
            accuracy (typical)        tokens/ticket
0-shot      ~72%                      ~30
5-shot      ~83%                      ~180
CoT-5       ~86-88%                   ~400-600
```

(The exact deltas depend on model tier — small models gain more from scaffolds; frontier models often need only the contract. Re-measure on model upgrades; a pinned alias will drift.)

## 6.5 Troubleshooting the Classics

| Symptom | Likely cause | Fix |
| :-- | :-- | :-- |
| Label format drifts (`Escalation`) | Inconsistent labels across shots | Byte-identical label set in prompt + eval + code |
| Model copies the last example's opening | Recency bias on position 5 | Make the final shot a clean typical case; test rotated orders |
| High accuracy on dev, tanks in prod | Shots don't match production mix | Re-sample shots from recent tickets; keep edge cases |
| CoT reasons correctly, answers wrong | Malformed answer separator | Pin `Reasoning:` / `Answer:` markers; parse code-side |
| 5 shots worse than 1 | Shots contradict each other or the contract | Audit for internal contradiction; drop the offender |

## 7. Common Pitfalls

| Pitfall | Fix |
| :-- | :-- |
| Examples are five copies of the easy case | Match production distribution + edge cases |
| Label formats drift (`Escalate` vs `escalate`) | One canonical label set, byte-identical |
| Last example is an outlier | Make position 5 a clean, typical, correct case |
| CoT everywhere "to be safe" | Gate CoT on eval evidence; keep it off high-volume paths |
| Few-shot after fine-tuning confusion | Few-shot ≠ training; nothing is learned — every call re-reads the examples |

## 8. Practice

**Guided exercise.** Build the 0/1/3/5-shot ladder for the refund classifier on 20 of your own labeled tickets. Record accuracy per step. Find the shot-count where gains flatten.

**Independent exercise.** Deliberately corrupt one example's label; re-run. Observe the silent accuracy drop — this is why evals gate merges (26.2.2).

**Challenge.** Add a "plan-then-answer" variant (plan → answer) and compare against CoT-5 on the same tickets: accuracy, tokens, latency.

**Assessment checklist**

- [ ] I can choose 0/1/3/5+ shots deliberately, not by default.
- [ ] I check ordering/recency effects before shipping a prompt.
- [ ] My examples match the production distribution, including an "other" case.
- [ ] I know how labels leak the task and keep one canonical set.
- [ ] I can state two situations where CoT is the wrong tool.
