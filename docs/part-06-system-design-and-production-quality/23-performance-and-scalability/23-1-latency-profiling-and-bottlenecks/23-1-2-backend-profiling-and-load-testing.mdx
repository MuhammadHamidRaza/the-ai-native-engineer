The storefront is fixed, the page loads fast — and `POST /v1/orders` still takes two seconds at peak. Server latency is a different discipline: **profiles, not audits; load tests, not vibes.** This lesson gives ShopCore a measured backend story: a real V8 CPU profile walkthrough, event-loop lag, a 100-VU k6 test with thresholds, and the triage method for answering "is it CPU, IO, the database, or the network?"

## 1. Before You Profile — State the Scenario

ShopCore load scenario (use these targets in every experiment below):

```text
Endpoint mix (read-heavy, like real traffic):
  GET  /api/products          70%
  GET  /api/products/:id      20%
  POST /v1/orders             10%

Pass criteria (fail the build otherwise):
  http_req_failed  rate < 0.01
  http_req_duration p(95) < 240 ms   p(99) < 300 ms   # NFR-001: checkout server-time p99 ≤ 300 ms
  checks           rate > 0.99
```

Averages hide everything. **p50** tells you the median user; **p95/p99** tell you who is suffering. A 120 ms average with an 8% tail at 2 s is a broken page for 1 in 12 users — and invisible in the average.

## 2. `node --prof` — The V8 CPU Profile Walkthrough

Node's built-in profiler is free and always there. Run the API with it:

```bash
# macOS/Linux/WSL2 — load the server briefly, then Ctrl-C
node --prof src/server.js
# ...hit it with: npx autocannon -c 25 -d 20 http://localhost:3000/api/products...

# A file appears: isolate-0xnnnnnnnnnnnn-vNNNN-NNN.log
node --prof-process isolate-0x*-*.log > profile.txt
```

Reading `profile.txt` — the sections that matter:

```text
 [JavaScript]:
   ticks  total  nonlib   name
    2412   78.9%   85.4%  LazyCompile: *serialize /app/src/lib/serialize.js:12:15
     802   26.2%   28.4%  LazyCompile: *applyQuery /app/src/db/products.js:44:9
     311   10.2%   11.0%  LazyCompile: *formatPrice /app/src/lib/money.js:8:20

 [C++]:
     ...   (V8 internals — usually small and not actionable)

 [Summary]:
   ticks  total  nonlib   name
   3089  100.0%  100.0%   JavaScript
     96    3.1%            GC
     61    2.0%            C++, Shared libraries
```

- **ticks** = samples of the stack when a timer fired (roughly every 1 ms). Percentages are shares of samples, not exact ms.
- Hot path here is `serialize` — ShopCore was re-stringifying every product on every cache miss. Fix: cache the serialized JSON, not just the object (see [23.2.1](/book/part-06-system-design-and-production-quality/23-performance-and-scalability/23-2-caching-and-horizontal-scaling/23-2-1-redis-cache-invalidation-and-rate-limiting)).
- **GC** consistently above ~15–20% ticks → allocation churn; look for objects rebuilt per request that could be reused/frozen.

Modern alternative: `node --cpu-prof src/server.js` writes a `.cpuprofile` you open in Chrome DevTools (`chrome://inspect` → Open dedicated DevTools for Node → Profiler) — flame-graph view, same data. For "something is wrong but I don't know what," `npx clinic doctor -- node src/server.js` (clinic.js by NearForm) wraps the process with event-loop-delay and flame heuristics and points at the category of problem; `clinic flame` gives an interactive flamegraph.

## 3. Event-Loop Lag — The One Number That Predicts "Node Is Dying"

Node runs your code on one thread. When a handler blocks it (sync crypto, JSON.parse of a 50 MB body, an infinite regex), **every** request waits — tail latency explodes while averages barely move.

```js
// src/lib/loop-lag.js — log p99 loop delay every 30 s
import { monitorEventLoopDelay } from 'node:perf_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  console.log('loop delay ms  p50=%s p95=%s p99=%s max=%s',
    h.percentile(50), h.percentile(95), h.percentile(99), h.max);
  h.reset();
}, 30000).unref();
```

Healthy ShopCore API under k6: p99 loop delay < ~50 ms. If p99 loop delay climbs above ~100 ms while CPU is low, something is **blocking** (find the sync call — it is never in your framework, it is always in your code or a dependency). Alert on this; it is the cheapest saturation signal you have (mirrors the USE saturation signal in [22.3.2](/book/part-06-system-design-and-production-quality/22-security-testing-and-observability/22-3-observability-and-incident-response/22-3-2-metrics-tracing-slis-slos-and-incident-response)).

## 4. k6 Load Test — The Build-Breaking Script

Install k6 from the [official docs](https://grafana.com/docs/k6/latest/set-up/installation/) (Windows: `winget install k6.k6` or Chocolatey; macOS: `brew install k6`; Linux: deb/rpm repos; or Docker: `docker run --rm -i grafana/k6 run -`).

```js
// loadtest/shopcore.js — 100 VUs, ramp up/down, build-failing thresholds
import http from 'k6/http';
import { sleep, check } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 100 },  // ramp
    { duration: '1m',  target: 100 },  // soak
    { duration: '15s', target: 0 },    // ramp down
  ],
  thresholds: {
    http_req_failed:   ['rate<0.01'],
    http_req_duration: ['p(95)<300', 'p(99)<800'],
    checks:            ['rate>0.99'],
  },
};

export default function () {
  const res = http.get('http://localhost:3000/api/products');
  check(res, {
    'status is 200': (r) => r.status === 200,
    'body has products': (r) => r.body.includes('"products"'),
  });
  sleep(1);
}
```

```bash
k6 run loadtest/shopcore.js
# k6 exits 0 when thresholds pass, 99 (or non-zero) when they don't — wire into CI the same way.
```

Key output to read (k6 prints these at the end):

```text
http_req_duration..............: avg=118ms min=41ms med=102ms max=1.9s p(90)=180ms p(95)=240ms p(99)=720ms
http_req_failed................: 0.00%  0 out of 18342
checks.........................: 100.00% ✓ 36684  ✗ 0
```

Reading it: p95 = 240 ms means 95% of requests finished under 240 ms; p99 = 720 ms is your tail; `max` is the single worst request — always look at it. `checks` is your correctness gate (a 200 with a broken body still fails the test). Alternates if k6 doesn't fit your shop: **hey** (`hey -z 30s -c 100 http://localhost:3000/api/products`), **vegeta** (Go, scriptable with files), **autocannon** (Node-native: `npx autocannon -c 100 -d 30 http://localhost:3000/api/products`).

## 5. USE vs RED — Two Triage Questions

| Method | Question | Look at | When |
| :-- | :-- | :-- | :-- |
| **RED** (services) | Do users hurt? | Rate, Errors, Duration | First stop for any alert: are requests slow or failing, and where |
| **USE** (resources) | Which organ is failing? | Utilization, Saturation, Errors | After RED says yes: CPU, DB pool wait, Redis memory, loop-lag saturation |

Flow: page → RED (which route, which status, p99?) → trace ([22.3.2 spans](/book/part-06-system-design-and-production-quality/22-security-testing-and-observability/22-3-observability-and-incident-response/22-3-2-metrics-tracing-slis-slos-and-incident-response)) → USE on the saturated resource → profile the culprit.

## 6. Bottleneck Triage — CPU vs IO vs DB vs Network

```text
  p99 high & CPU high & loop-lag high  -->  CPU-BOUND   profile with --prof; fix hot code / cache serialization / offload
  p99 high & CPU low  & span = pg      -->  DB-BOUND    EXPLAIN ANALYZE (24.1.2); pool starvation (24.2.1); locks
  p99 high & span = stripe.com         -->  IO-BOUND    timeouts + retries (21.4.2); move off request path (queue)
  p99 high & span = DNS/TLS            -->  NETWORK     reuse agents (keep-alive), preconnect, HTTP/2, proximity
  p99 high & span = Redis              -->  CACHE       23.2.1: key churn, big values, no maxmemory policy
```

ShopCore's real first miss: the catalog handler parsed `JSON.parse(row.attrs)` for 400 rows per request **on the main thread** — k6 showed p(99) = 1.9 s with CPU at 40% and zero DB time above 30 ms. The fix was §2's serialize cache plus a single `prepared` attribute query; p99 dropped under 200 ms with no new hardware.

## 7. Troubleshooting Table

| Symptom | Likely cause | Fix |
| :-- | :-- | :-- |
| k6 fails `rate<0.01` but app "feels fine" | Bulkheads full: pool = 10, 100 VUs → 90 wait | Size pool per 24.2.1; or lower VUs; check `pg_stat_activity` |
| p99 spikes only under ramp, not soak | Cold caches + JIT warmup | Warm the cache in k6 `setup()`; ignore first 5 s in analysis |
| `node --prof` shows 40% in `GC` | Allocation churn | Reuse objects; avoid per-request closures capturing big graphs |
| autocannon vs k6 disagree wildly | Different concurrency model | Trust the tool matching your pipeline; k6 for thresholds in CI |
| Profile looks like tiny ticks everywhere | Sampling too coarse | Use `--cpu-prof` and Chrome DevTools flamegraph |
| One route slow, rest fine | N+1 on that route | See [24.2.1](/book/part-06-system-design-and-production-quality/24-database-performance-and-operations/24-2-connection-pooling-and-operational-scale/24-2-1-connection-limits-locking-and-n-plus-1-queries) |

## 8. Practice

**Guided.** Run §4's k6 script against local ShopCore. Record p50/p95/p99. Break one thing on purpose (e.g. re-add a `JSON.parse` in a loop) and watch p(99) degrade. Revert, confirm green.

**Independent.** Run `node --prof` during a 20 s autocannon soak; produce `profile.txt`; name the top-3 tick owners; write one sentence on what you'd fix first.

**Challenge.** Add the loop-delay logger to ShopCore, run k6, log p99 loop delay at 50/80/100 VUs. Find the VU count where p99 latency and loop delay both bend upwards — that is your knee. Document it in the notebook.

**Assessment checklist**

- [ ] I can run k6 with build-failing thresholds and explain p50 vs p95 vs p99.
- [ ] I have read a real `--prof-process` output and found a hot function.
- [ ] I can place `monitorEventLoopDelay` in a service and know what p99 > 100 ms means.
- [ ] I triage with RED first, then USE — not by staring at a CPU graph.
- [ ] I know when a bottleneck is the database, the network, or the event loop.
- [ ] I can state ShopCore's load targets from memory (p99 ≤ 300 ms NFR-001, errors < 1%).
