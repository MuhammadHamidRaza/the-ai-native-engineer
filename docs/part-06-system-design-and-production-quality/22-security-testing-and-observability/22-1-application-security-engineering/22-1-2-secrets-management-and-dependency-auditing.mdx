Half of ShopCore's security posture is the code you write (22-1-1); the other half is the code and credentials you inherit. This lesson covers the two inheritance problems: the secrets that leak through git, CI logs and shoulder-surfing, and the dependencies that fail on someone else's CVE schedule. Both are process problems with exact, rehearsed answers.

## 1. Categorize Every Secret in ShopCore

| Category | Example | Where it lives | Rotation | Blast radius |
| :-- | :-- | :-- | :-- | :-- |
| Datastores | Postgres `app` user password | PaaS env var / Neon endpoint | 90 days | Full read/write of shop data |
| Third-party API keys | Stripe `sk_live_…` | PaaS secret store | On event + 180 days | Refunds, charges, customer PII |
| Webhook secrets | Stripe `whsec_…` | PaaS secret store | 180 days | Forged payment confirmations |
| JWT signing keys | RS256 keypair | Secret store + JWKS | 12 months (kid overlap) | Session forgery |
| SSH / CA | VPS access | `ssh-agent`, CA-signed certs | 90 days (cert), CA 2 years | Root on hosts |
| TLS private keys | shopcore.dev cert | ACME-managed | Auto (Let's Encrypt 90 days) | Impersonation |
| Redis auth | ACL password | PaaS secret store | 90 days | Cache poisoning, eviction |

Inventory rule: no secret enters the repo, the build logs, or the wiki. Every secret has exactly one owner and one rotation date in `docs/security/secrets.md` (values never included — names, locations, owners only).

## 2. Never in Git — and Why History Purge Is Not the Fix

If a secret ever lands in history, **it is compromised the moment it is pushed**, even in a private repo (forks, CI clones, mirrors). Purging history (`git filter-repo`, BFG) is hygiene, not remediation. The only real fixes, in order:

1. **Rotate immediately** — invalidate the leaked credential at the provider.
2. Audit its usage (Stripe: API logs show unknown IPs; PG: `pg_stat_activity` history / Neon activity).
3. Then purge history to prevent future leaks from cloning.

Prevention that actually works: `gitleaks` (or `trufflehog`) as a pre-commit hook **and** in CI (fail the build on new findings); `.gitignore` for `.env*`; GitHub secret scanning + push protection (free for public repos). Verify locally: `git log -S 'sk_live' --oneline` should return nothing.

## 3. Dev vs Prod — Two Worlds, Two Controls

**Dev:** `.env` (never committed), seeded local Postgres/Redis (docker compose), Stripe **test-mode** keys only — `sk_test_…` cannot touch real money. Developers who cannot tell test from live keys apart do not touch payments code.

**Prod:** secrets injected by the platform — Render/Railway/Fly env vars, AWS/GCP secret managers (see [19.2.2](/book/part-05-deployment-cloud-and-devops/19-cloud-engineering-devops-cicd-and-iac/19-2-devops-workflows-and-cicd-pipelines/19-2-2-testing-artifacts-ci-secrets-and-rollback-pipelines) on CI secrets), Kubernetes Secrets (or better, Sealed-Secrets/External Secrets Operator) — never in Dockerfiles, never in `docker-compose.yml` committed with values. [16.1.1](/book/part-05-deployment-cloud-and-devops/16-deployment-foundations-domains-dns-and-hosting/16-1-deployment-fundamentals-and-hosting-models/16-1-1-local-to-production-builds-ports-env-vars-and-cors) covers the dev/prod env split end-to-end.

## 4. Rotation Without Downtime

- **Stripe:** create restricted/second key (dashboard → Developers → API keys), deploy with new key while old still valid, verify charges against old-vs-new usage, revoke old. Stripe supports rolling keys this way — no outage window.
- **AWS:** two access keys per user — app runs key A, rotate to key B, deactivate (not delete) A, watch 24 h of `AccessKeyLastUsed`, delete A after zero use. IAM Access Analyzer flags stale keys > 90 days unused.
- **GCP:** service accounts + **workload identity federation** (no long-lived keys at all) or rotate JSON keys on schedule; enable audit logs for key usage.
- **JWT:** publish JWKS with two `kid`s during rotation overlap; tokens issued under old kid verify until expiry; new kid signs new tokens; drop old after TTL + grace.
- **Webhook secret:** Stripe lets you roll `whsec_` with both active during transition; re-register your endpoint with the new secret, deploy, then retire the old.

Every rotation is **programmatic** — via provider CLI/API, never hand-copied from a dashboard screenshot into chat. Script it in `scripts/rotate-*.ps1` / `.sh`; a rotation you must do by hand is a rotation you will skip during an incident.

## 5. Least Privilege and Blast Radius

- Postgres: app runtime role has `SELECT/INSERT/UPDATE/DELETE` on `ordering.*` only — no DDL, no role grants, no `postgres` superuser anywhere near the app. Migrations run under a separate short-lived role.
- Stripe keys: **restricted keys** per consumer — the analytics exporter gets read-only `charges:read`; the checkout API gets `charges:write` only. Webhook signing secret separate from API key.
- Redis ACL: `AUTH` per consumer group; analytics user is GET-only on `catalog:*`.
- CI tokens: least-scope GitHub Actions `GITHUB_TOKEN`; deploy keys never reused for PRs from forks (forks get no secrets at all).

Blast radius test: *if this credential leaked publicly right now, what is the worst damage in 60 minutes?* If the answer is "unbounded", the credential is over-scoped — fix the scope, not the password length.

## 6. Rotation Drill — Quarterly, 30 Minutes, No Heroes

Rehearse on staging: rotate Stripe webhook secret live, zero 5xx, webhook replay confirms signature validation works on the new secret. Record duration; target ≤ 30 minutes; each drill finds at least one book error or stale assumption. Alerting on anomalies: API key usage from unexpected IPs (provider dashboards + Stripe Radar for rules), sudden 403 spikes, secret-scanning hits, and PG connection from non-app IPs — all page to #sec-oncall.

**mTLS (pointer):** service-to-service mutual TLS (Linkerd/Istio or plain cert-manager issuers) removes bearer secrets between your own services entirely; ShopCore adopts it when the second service exists (21.3.1's extraction trigger), not before.

## 7. Dependency Auditing — the Cadence

```bash
# PR-time (CI gate, fail on high+critical)
npm audit --omit=dev --audit-level=high
npx snyk test --severity-threshold=high        # or rely on Dependabot
npx license-checker --summary

# Weekly
npx depcheck                                    # find unused deps — remove them
npx npm-check-updates --target minor            # propose bumps

# Quarterly
npx @cyclonedx/cyclonedx-npm --output-file sbom.json   # SBOM artifact
git diff package-lock.json                      # eyeball transitive churn
```

Rules: **lockfile committed** (npm `package-lock.json`); `engines` + `.nvmrc` (Node LTS, e.g. `22.x`); no `^` on security-critical deps (`stripe`, `jsonwebtoken` pinned exact); `overrides` for transitive CVEs the maintainer hasn't patched; zero known-unused deps (every `devDependencies` entry must justify itself).

## 8. Supply Chain Incidents — the Two Canonical Lessons

- **SolarWinds (2020):** the build system was the attack surface — a poisoned update shipped signed by the legitimate vendor. Lesson: pin CI actions to full commit SHAs (`uses: actions/checkout@<full-40-char-sha> # v4.x.y`) — not tags, which are movable, not branches, which move constantly — verify artifact attestations, and treat build pipelines as production.
- **event-stream / flatmap-stream (2018):** a maintainer added a dependency that shipped malicious payload targeted at one downstream app (Copay). Lesson: install-time review matters — `npm ci` from lockfile, no fresh installs on deploy, and Dependabot PRs reviewed by a human who reads the diff, not just the green badge.

## 9. Troubleshooting

| Symptom | Cause | Fix |
| :-- | :-- | :-- |
| `git clone` contains `sk_live` in old commits | Leak before hooks existed | Rotate now; purge history; audit usage; add gitleaks pre-commit |
| Staging works, prod 401s after rotation | Old key cached in one instance | Rolling deploy + dual-key window; verify with two smoke orders |
| `npm audit` 400 vulnerabilities, nobody cares | No triage policy | Group by reachability (prod only, exploit path exists?); fix criticals in 7 days |
| Dependabot PRs rot unmerged | No assignment | Auto-assign CODEOWNERS; CI runs full suite; merge train Friday |
| Secret in CI log output | `echo $SECRET` debugging | Mask in CI settings; lint workflows for secret interpolation |

## 10. Practice

**Guided exercise.** Create a scratch repo with a fake `stripe.key` in a file; run `gitleaks detect` and pre-commit; push with GitHub push protection enabled and watch it block.

**Independent exercise.** Write `scripts/rotate-stripe-webhook.ps1` (or `.sh`) for staging: dual-registration of webhook, deploy, verify with Stripe CLI `stripe trigger payment_intent.succeeded`, retire old. Time yourself.

**Challenge.** Produce `sbom.json` for ShopCore, then answer: which direct dependencies have no commit in 18 months, which have known CVEs exploitable from prod code paths, and which two would you remove first and why?

**Assessment checklist**

- [ ] I can name every ShopCore secret category, its owner and its rotation date.
- [ ] I know why history purge does not un-leak a secret, and what does.
- [ ] I can rotate Stripe, AWS, JWT and webhook secrets without downtime.
- [ ] I can scope any ShopCore credential to minimal blast radius on demand.
- [ ] I have run the rotation drill, produced an SBOM, and removed one unused dependency.
