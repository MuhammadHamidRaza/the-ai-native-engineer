The frontend is what users see; the **backend** is where security, business truth, database writes, provider secrets, third-party API orchestration, background ingestion, and AI calls actually execute. Never trust browser JavaScript with authorization rules, subscription tiers, workflow state checks, or `GEMINI_API_KEY` credentials—every authoritative decision executes behind authenticated server boundaries.

**The AI-Native Engineer** trains you fluently across both dominant modern API ecosystems—**Python (3.13+ + FastAPI)** in [Part 03](/book/part-03-python-development) (`40 hours`) and **Node.js (24 / 26 Active LTS) + TypeScript** in [Part 04](/book/part-04-databases-backend-and-full-stack-development) (`124 hours`)—because modern startups and enterprise AI teams routinely pair them together based on workload strengths.

## Five Non-Negotiable Backend Habits Across Parts 03–04

Whether writing a route handler in **FastAPI** or **Express / Next.js Route Handlers**, every production service taught in this curriculum enforces five boundaries before touching business logic:

1. **Strict input validation at the edge:** Parse every request body, path parameter, and query string through Pydantic or Zod immediately—returning explicit `400` or `422` diagnostics before querying PostgreSQL or calling an AI model.
2. **Authentication *before* authorization:** Verify *who* the caller is (`401 Unauthorized` when missing or expired), then verify *what resource* that caller owns inside the workspace (`403 Forbidden` when accessing another tenant's record). Never rely on "hidden unguessable IDs" alone without checking ownership in SQL (`WHERE id = $1 AND workspace_id = $2`).
3. **Structured, safe error envelopes:** Never expose raw SQL constraint strings, file system paths, or stack traces directly to external browsers. Log the full traceback server-side tagged with a unique `request_id` and return a predictable JSON error object to the client.
4. **Explicit timeouts and bounded retries on external I/O:** Every webhook delivery, payment call, or LLM completion wraps an explicit timeout (`AbortSignal.timeout()` in Node.js or `httpx.Timeout` in Python) and bounded exponential backoff only on safe transient `429`/`5xx` errors—never infinite retry loops.
5. **Stateless request processes + persistent database job state:** Process memory vanishes on every deploy or crash. Long-running ingestion pipelines and multi-step agent runs store progress checkpoints in PostgreSQL tables rather than module-level dictionaries or arrays.

Compare how clean boundary validation and tenant isolation look in **FastAPI**:

```python
from fastapi import Depends, FastAPI, HTTPException, status
from pydantic import BaseModel, Field

app = FastAPI()

class CreateNoteRequest(BaseModel):
    workspace_id: str = Field(min_length=8)
    title: str = Field(min_length=1, max_length=160)
    body: str = Field(min_length=1, max_length=10_000)

@app.post("/v1/notes", status_code=status.HTTP_201_CREATED)
async def create_note(
    payload: CreateNoteRequest,
    actor: dict = Depends(require_authenticated_user),
):
    if payload.workspace_id not in actor["workspace_ids"]:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Actor does not have write access to target workspace.",
        )
    # Proceed with parameterized PostgreSQL INSERT scoped to payload.workspace_id
    return {"status": "created", "workspace_id": payload.workspace_id}
```

## Predictable JSON Error Envelopes Across Node.js and Python

Whether a browser React hook calls FastAPI or a Next.js Route Handler, frontend components handle failures cleanly only when backends return one predictable error shape carrying a server correlation ID—never leaked raw stack traces:

```typescript
// Standardized API error response helper in TypeScript backend services
export function errorEnvelope(
  statusCode: number,
  code: string,
  message: string,
  requestId: string
) {
  return Response.json(
    {
      error: { code, message, requestId },
    },
    { status: statusCode }
  );
}
```

Pairing structured error envelopes (`VALIDATION_ERROR`, `FORBIDDEN_WORKSPACE`, `UPSTREAM_TIMEOUT`) with `AbortSignal.timeout(10_000)` on external HTTP calls prevents frozen browser tabs and turns production support tickets into instant `requestId` log lookups (`Ch 13 & Ch 22`).

## Synchronous Request Path vs. Asynchronous Worker Path

One critical architectural distinction you master in **Part 04** and **Part 06** is deciding what belongs inside an HTTP request handler versus what belongs in a background worker:
- **Keep inside the HTTP request (`< 300ms`):** Authentication checks, single-row or small transactional reads/writes, pre-signed upload URL generation, and enqueueing background work (`202 Accepted`).
- **Move into a background worker:** Parsing a 40-page PDF, generating 300 vector embeddings, sending batch customer notifications, or running multi-step tool chains. Keeping 45-second jobs inside synchronous HTTP requests exhausts server worker threads, triggers reverse-proxy `504 Gateway Timeout` errors, and breaks user refreshes.

## Common Backend Anti-Patterns to Catch Early

- **Trusting client-supplied `user_id` or `role` fields:** Accepting `role: "admin"` inside a JSON signup body lets any attacker escalate privileges with one `curl` command. Derive caller identity strictly from verified server session cookies or signed tokens.
- **Unbounded list endpoints (`SELECT * FROM logs`):** Returning an entire table without `LIMIT` and cursor/offset pagination works with 20 test rows and crashes production servers once a tenant hits 250,000 rows.
- **Swallowing exceptions with `catch (err) {}` or bare `except Exception: pass`:** Silent failure leaves users staring at a frozen spinner while databases hold half-written state and logs record nothing.

## Practical Exercise: Audit a Vulnerable Route Specification

Consider a naive API endpoint `POST /api/transfer` that accepts `{ fromAccountId, toAccountId, amount }`, reads `fromAccountId` directly from the JSON body without checking the logged-in session user, subtracts `amount` in one SQL statement, adds `amount` in a second non-transactional SQL statement, and does not check if `amount <= 0`. List every security, concurrency, and data-integrity failure in that handler and write the five-step guard order that fixes all of them.

Check your five-step fix against production backend discipline: (1) derive `actorUserId` strictly from the verified session (`401` if unauthenticated), (2) enforce `amount > 0` integer cents via Zod/Pydantic (`422` otherwise), (3) reject unless `actorUserId` owns `fromAccountId` (`403`), (4) wrap debit + credit inside one PostgreSQL `BEGIN ... COMMIT` transaction locking rows deterministically with `CHECK (balance_cents >= 0)`, and (5) enforce an explicit `idempotency_key` unique constraint so duplicate retries never double-transfer funds.

Equally important in both **Node.js** and **FastAPI** backends (`Ch 12–13`) is clean connection-pool lifecycle hygiene: reuse one shared pool instance across requests rather than opening a brand-new TCP/TLS PostgreSQL connection per HTTP call, close pools cleanly on `SIGTERM` shutdown, and log latency + `requestId` deterministically on both `2xx` completions and `4xx`/`5xx` failures.
