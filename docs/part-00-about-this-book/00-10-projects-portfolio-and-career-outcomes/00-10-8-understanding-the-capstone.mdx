## Choosing a High-Value Capstone Scope (And Filtering Bad Ideas Early)

The most dangerous capstone failure happens in **Hour 1**: choosing a scope meant for a 15-person company across six months (*"Build a multi-tenant AI ERP replacing Salesforce, Jira, and QuickBooks"*) or choosing a thin toy (*"Build a single-page chatbot that summarizes pasted paragraphs"*).

Evaluate your candidate Capstone idea against three sanity gates before writing your first migration:
1. **Does it have non-trivial deterministic state?** If removing the AI model leaves *nothing* except a blank screen, the project lacks genuine backend and relational rigor. Strong capstones enforce user roles, documents, runs, approvals, and audit trails in PostgreSQL cleanly.
2. **Does AI add clear leverage while staying verifiable?** Can an operator inspect *why* the AI proposed an output (clickable source chunks, highlighted invoice rows, traceable tool call traces) and approve/correct it cleanly?
3. **Can Slice 1 ship completely in 36 hours?** If the system needs four third-party OAuth integrations, mobile native apps, and custom Stripe billing webhooks just to demonstrate the core workflow, trim aggressively until the **single core operational loop** fits comfortably inside 36 hours with time left for evaluation and deployment polish.

## Inside the Chapter 42 Code & Evaluation Standard

Your final capstone repository demonstrates engineering rigor cleanly inside the codebase itself—not inside slide decks alone. At minimum, reviewers look for disciplined data integrity, bounded AI invocation, and reproducible evaluation proof:

```sql
-- Representative Capstone Spine: Auditable Workflow Runs + Human Feedback Ledger
CREATE TABLE capstone_runs (
  id              UUID PRIMARY KEY,
  workspace_id    UUID NOT NULL,
  input_hash      TEXT NOT NULL,
  status          TEXT NOT NULL CHECK (status IN ('QUEUED','NEEDS_REVIEW','APPROVED','FAILED')),
  ai_output_json  JSONB NOT NULL,
  human_edit_json JSONB,
  prompt_tokens   INTEGER NOT NULL DEFAULT 0,
  output_tokens   INTEGER NOT NULL DEFAULT 0,
  latency_ms      INTEGER NOT NULL DEFAULT 0,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (workspace_id, input_hash)
);
```

Notice four production signals packed into just one table: tenant isolation (`workspace_id`), webhook/upload duplicate protection (`UNIQUE (workspace_id, input_hash)`), explicit finite state machine (`CHECK status`), and side-by-side FinOps + accuracy learning telemetry (`human_edit_json`, tokens, latency).

Pair that schema with a runnable **Golden Evaluation Runner (`Ch 36`)** checked right into `evals/` that asserts schema validity, forbidden hallucination patterns, expected citations, and token ceiling compliance before any release ships:

## Capstone Readiness Gate: Hour-36 Ship-Day Checklist

Before calling Chapter 42 complete and presenting your flagship project inside your portfolio:
1. **Clean Fresh-Clone Boot:** A reviewer cloning the repo, copying `.env.example`, and following `README.md` boots database, backend, and frontend smoothly in under 5 minutes.
2. **Negative-Path Proof:** Unauthenticated requests return `401`, cross-workspace reads return `403/404`, malformed payloads fail with explicit validation messages, and upstream AI timeouts surface recoverable operator states.
3. **Live Demo Safety:** Seeded anonymized fixtures allow instant exploration without requiring visitors to create external accounts or upload private production data.
4. **Honest Trade-Off Docs (`ADRs`):** Written documentation states clearly what was intentionally kept deterministic vs. AI-assisted, known failure boundaries from your eval report, and concrete Slice 2 next steps.

## Capstone Verification Rubric: Deterministic vs. AI Boundaries

Before you mark any **Chapter 42** build ready for review, verify how responsibilities cleanly split across deterministic engineering and probabilistic AI components inside your codebase:

| Failure Scenario | Incorrect Toy Handling | Chapter 42 Production Handling |
| :--- | :--- | :--- |
| **LLM invents an invalid price or unknown SKU** | Silently stores hallucinated numbers in Postgres and displays `$NaN` | Zod/Pydantic schema rejects malformed shape; deterministic SQL lookup flags unknown SKU as `NEEDS_REVIEW` cleanly |
| **Duplicate webhook or user double-click arrives** | Triggers two expensive LLM runs and creates duplicate invoice records | PostgreSQL `UNIQUE (workspace_id, input_hash)` returns existing `run_id` idempotently without re-billing tokens |
| **Cross-tenant record ID passed in URL or API body** | Queries `WHERE id = $1` only, leaking another organization's documents | Every SQL `SELECT`/`UPDATE` and `pgvector` query binds `WHERE workspace_id = $1 AND id = $2` server-side |
| **Upstream model API returns `429` or stalls 20s** | Unhandled promise rejection returns HTTP `500` HTML stack trace to UI | Bounded timeout (`AbortSignal.timeout`) transitions row to `FAILED` with operator retry button and preserved input |
| **Unbounded agent tool loop burns quota** | Recursive `while(true)` loop calls tools 40 times on an ambiguous ticket | Server enforces `maxSteps = 5` and daily workspace token ceiling (`ai_usage_events`), failing safely into human review |

## Sample Runnable Golden Evaluation Script (`evals/run_evals.ts`)

Instead of eyeballing three prompts in Swagger, Chapter 42 requires a scripted evaluation harness that runs cleanly in CI or before every release—reporting concrete pass counts rather than guesswork:

```typescript
// evals/run_evals.ts — deterministic + AI quality regression gate for Chapter 42
import { readFileSync } from "node:fs";
import { runWorkflowPipeline } from "../src/services/pipeline";

interface GoldenCase {
  id: string;
  inputText: string;
  expectedStatus: "APPROVED" | "NEEDS_REVIEW";
  requiredCitationId: string | null;
  maxAllowedTokens: number;
}

const dataset: GoldenCase[] = JSON.parse(
  readFileSync("evals/golden_cases.json", "utf8")
);

async function main() {
  let passed = 0;
  for (const tc of dataset) {
    const start = performance.now();
    const out = await runWorkflowPipeline(tc.inputText, { dryRun: true });
    const elapsedMs = Math.round(performance.now() - start);

    const statusOk = out.status === tc.expectedStatus;
    const citationOk =
      tc.requiredCitationId === null ||
      out.citations.some((c) => c.id === tc.requiredCitationId);
    const budgetOk = out.totalTokens <= tc.maxAllowedTokens;

    if (statusOk && citationOk && budgetOk) {
      passed += 1;
    } else {
      console.error(
        `[FAIL] ${tc.id} status=${out.status} (expected ${tc.expectedStatus}) ` +
        `tokens=${out.totalTokens} elapsed=${elapsedMs}ms`
      );
    }
  }

  console.log(`Golden Eval Summary: ${passed}/${dataset.length} passed`);
  if (passed < Math.floor(dataset.length * 0.9)) {
    process.exitCode = 1; // Block release if accuracy drops below 90% threshold
  }
}

main();
```

Notice why an automated evaluation harness like this transforms how senior engineers evaluate your Capstone:
1. Every regression caused by an edited system prompt, model upgrade, or chunk-size change is exposed numerically in seconds (`18/20 passed`) instead of sneaking silently into production.
2. Putting `dryRun: true` inside the harness keeps automated evaluations strictly isolated from live side-effect tables and customer webhooks.
3. Recording `evals/baseline_report.md` inside your repository—explicitly noting which 2 cases out of 20 still require human review and why—proves authentic engineering honesty (`00.4.6`).

## Structuring Your 90-Second Demo & Handover Walkthrough

Even a clean full-stack architecture loses impact if a hiring manager or stakeholder cannot grasp its value inside two minutes. Pair your deployed URL and GitHub repo with a crisp, unhurried 90-second video walkthrough following this exact beat sheet:
- **0:00–0:15 (Operational Context):** State the manual workflow bottleneck directly (*"Warranty coordinators spent 18 minutes cross-checking messy PDFs against ERP contracts; Slice 1 cuts review to under 3 minutes"*).
- **0:15–0:45 (Happy Path + Discrepancy Catch):** Upload a realistic messy invoice fixture, show streaming progress, and point out how deterministic code caught a unit-price mismatch beside clickable `pgvector` contract citations.
- **0:45–1:05 (Approval Gate & Audit Log):** Click **Approve with Correction**, refresh the browser cleanly to prove PostgreSQL persistence, and inspect the audit ledger.
- **1:05–1:30 (Tests, Evals & Known Bounds):** Show `npm test` + `evals/run_evals.ts` passing in terminal, highlight one ADR (`docs/adr/001-*.md`), and close calmly.
