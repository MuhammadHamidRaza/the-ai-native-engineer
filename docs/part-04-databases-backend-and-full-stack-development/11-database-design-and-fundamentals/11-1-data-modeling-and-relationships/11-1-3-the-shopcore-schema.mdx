Every SQL example in this book runs against **one schema and one seed dataset**: **ShopCore**, a small but realistic online store. This page is the canonical reference. Whenever any lesson says "using the ShopCore database," it means exactly what is written here — nothing else. Bookmark this page.

## 1. Why a Canonical Schema Matters

Tutorials fail when every lesson invents its own tables, column names and data types. A `products` table with `price` in one lesson, `price_cents` in another, and `product_id` in a third forces you to unlearn and re-learn in every chapter. ShopCore fixes this:

- **One set of table names, column names and data types** used everywhere.
- **One seed dataset** so example outputs are reproducible on your machine.
- **One ER diagram** you can redraw from memory after Chapter 11.

## 2. The ShopCore Entity-Relationship Diagram

Read the diagram using **crow's foot notation**. A line ending in a three-pronged fork (`\/ <` ) means "many". A short single bar (`|`) means "one". `\|o--` means "zero or one".

```text
users (1) ──────────────< (N) orders (1) ──────────< (N) order_items >──────── (1) products
                                    |                                          │
                                    │                                        (N)
                                    │                                          │
                                (1) │                                     (1) categories
                                    v                                         
                                payments
```

In words:

| Relationship | Reading | Cardinality | Where the foreign key lives |
| :-- | :-- | :-- | :-- |
| `users` → `orders` | A user places many orders | 1 : N | `orders.user_id` |
| `orders` → `order_items` | An order contains many line items | 1 : N | `order_items.order_id` |
| `products` → `order_items` | A product appears in many line items | 1 : N | `order_items.product_id` |
| `categories` → `products` | A category groups many products | 1 : N | `products.category_id` |
| `orders` → `payments` | An order has at most one payment | 1 : 1 (optional) | `payments.order_id` is `UNIQUE` |

`order_items` is the **junction table** that turns "orders ↔ products" into a proper many-to-many relationship. It also carries the historical price snapshot (`unit_price_cents`) so future catalog price changes never rewrite past receipts.

## 3. The Canonical DDL

Use **PostgreSQL 18** (installed in Chapter 12). Open your database client once you finish installing it, select or create the `shopcore` database, and run this script exactly as written.

```sql
-- shopcore_schema.sql — canonical ShopCore schema (PostgreSQL 18)
DROP TABLE IF EXISTS payments, order_items, orders, products, categories, users CASCADE;

CREATE TABLE users (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,
  full_name     TEXT NOT NULL,
  role          TEXT NOT NULL DEFAULT 'customer' CHECK (role IN ('customer', 'admin')),
  password_hash TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE categories (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  TEXT NOT NULL UNIQUE,
  slug  TEXT NOT NULL UNIQUE
);

CREATE TABLE products (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  category_id BIGINT NOT NULL REFERENCES categories(id) ON DELETE RESTRICT,
  sku         TEXT NOT NULL UNIQUE,
  title       TEXT NOT NULL,
  price_cents INTEGER NOT NULL CHECK (price_cents >= 0),
  stock_qty   INTEGER NOT NULL CHECK (stock_qty >= 0),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE orders (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  status     TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE order_items (
  id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id         BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id       BIGINT NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  qty              INTEGER NOT NULL CHECK (qty > 0),
  unit_price_cents INTEGER NOT NULL CHECK (unit_price_cents >= 0)
);

CREATE TABLE payments (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id     BIGINT NOT NULL UNIQUE REFERENCES orders(id) ON DELETE RESTRICT,
  amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0),
  provider     TEXT NOT NULL CHECK (provider IN ('manual', 'stripe', 'paypal')),
  status       TEXT NOT NULL DEFAULT 'succeeded' CHECK (status IN ('succeeded', 'failed', 'refunded')),
  paid_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
CREATE INDEX idx_order_items_product_id ON order_items (product_id);
CREATE INDEX idx_products_category_id ON products (category_id);
```

### Why each column exists

| Table | Column | Why it exists |
| :-- | :-- | :-- |
| `users` | `id` | Stable surrogate primary key. Emails change; ids never do. |
| `users` | `email` (`UNIQUE`) | Business identifier for login; database prevents duplicate accounts. |
| `users` | `role` | `customer` vs `admin` for Chapter 13 authorization. |
| `users` | `password_hash` | Scrypt hash set at registration (Chapter 13) or seeded for the three public demo accounts (§4) — nullable in the schema so the column exists before auth does. |
| `categories` | `slug` (`UNIQUE`) | URL-friendly stable identifier (`/shop/hardware`) for routing and APIs. |
| `products` | `price_cents` | **Integer cents, never floating-point dollars.** `12900` means $129.00. Floats accumulate rounding errors; money must not. |
| `products` | `stock_qty` | Enforced `>= 0` so overselling is rejected by the database itself. |
| `products` | `category_id` | FK with `RESTRICT` delete so a category can't vanish leaving orphan products. |
| `orders` | `status` | `CHECK` constraint limits lifecycle to known states — typos like `'Paid'` are rejected at the source. |
| `order_items` | `qty`, `unit_price_cents` | `unit_price_cents` is the **historical snapshot** of the price actually paid (see 11.1.2). |
| `payments` | `order_id` (`UNIQUE`) | One payment per order; the FK + UNIQUE enforces it. |

### Verify the seed worked

Run these two queries after seeding:

```sql
SELECT id, email, full_name, role FROM users ORDER BY id;
-- Expect exactly 3 rows: Ada (1), Grace (2), Linus (3).

SELECT o.id AS order_id, u.full_name, o.status,
       COALESCE(SUM(oi.qty * oi.unit_price_cents), 0) AS total_cents
FROM orders o
JOIN users u ON u.id = o.user_id
LEFT JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, u.full_name, o.status
ORDER BY o.id;
-- Expect:
-- order_id 1 | Ada Lovelace   | paid    | 24700
-- order_id 2 | Ada Lovelace   | pending |  4500
-- order_id 3 | Grace Hopper   | pending |  5900
```

If your results differ, stop and fix the seed before continuing — every number you see in later lessons is computed from this dataset.

## 5. Loading the Schema into Your Database

You do not need to memorize this now; Chapter 12 teaches the full installation. Once PostgreSQL and `psql` are installed, the two files above are loaded with:

```bash
# Run these from the folder containing the .sql files
psql -U postgres -d shopcore -f shopcore_schema.sql
psql -U postgres -d shopcore -f shopcore_seed.sql
```

`psql` prints `CREATE TABLE` / `CREATE INDEX` / `INSERT 0 3` (rows inserted) for each statement. Any `ERROR:` line means something upstream went wrong — read it carefully; it names the exact statement that failed.
