**Chapter 15 is not a tutorial dump.** You will build **ShopCore** — a working online store — in nine milestones, exactly like a real contract: requirements → schema → backend → auth → frontend → tests → ship. Each milestone has complete instructions, expected outputs, and a checklist. Do them in order.

This is where Chapters 11–14 converge: the ER diagram, the queries, the API design, Git flow — all of it becomes one application.

## 1. What We're Building — Product Requirements

**ShopCore** — an online store with these capabilities:

| # | User story | Acceptance |
| :-- | :-- | :-- |
| 1 | As a visitor, I can browse the catalog (list products, view details) | Public `GET /api/v1/products` |
| 2 | As a customer, I can register and log in | `POST /api/v1/auth/register`, `/login`, `/logout`, `GET /auth/me` |
| 3 | As a customer, my catalog browsing is unrestricted, but checkout requires login | Protected write routes |
| 4 | As a customer, I can add products to a cart and place an order | `POST /api/v1/cart/items`, `POST /api/v1/orders/checkout` |
| 5 | My orders are mine alone — IDOR-proof | `WHERE user_id = $1` everywhere |
| 6 | Admins can add/update products; customers cannot | Role check + ownership |
| 7 | Catalog search finds products by keyword | `tsvector` from 12.3.3 |
| 8 | Admins can view a sales dashboard | `GET /api/v1/admin/sales` (aggregate query) |
| 9 | The store survives bad input | Zod validation + 400s |
| 10 | CI proves the build works | Lint + typecheck + `npm test` (14.3) |

**Out of scope (deliberately):** payments (a `payments` table exists — stub provider `manual`), image upload CDN, multi-tenancy. You can extend later — shipping beats scoping perfectly.

## 2. System Architecture

```text
┌─────────────┐      HTTPS       ┌──────────────────┐   SQL    ┌────────────┐
│ React +     │ ───────────────> │ Express 5 API    │ ───────> │ PostgreSQL │
│ Vite (SPA)  │  fetch() +       │ port 4000        │  pg Pool │ shopcore   │
│ port 5173   │  HttpOnly cookie │ all /api/v1/*    │          │ 11.1.3     │
└─────────────┘                  └──────────────────┘          └────────────┘
                                       │ Node API :4000 also serves /uploads or static in prod
                                       ▼
                              Browser dev tools: Application → Cookies → session (HttpOnly)
```

- **Dev:** two processes — `npm run dev` in `apps/web` (Vite :5173), `npm run dev` in `apps/api` (Express :4000); Vite proxies `/api` → `:4000` so the SPA can use relative URLs.
- **Prod:** build SPA (`npm run build`) → Express serves `apps/web/dist` statically — one origin, no CORS, same cookie.

Every file has a job; nothing in this tree is decorative. `db/migrations/001_init.sql` is exactly the DDL from [11.1.3](/book/part-04-databases-backend-and-full-stack-development/11-database-design-and-fundamentals/11-1-data-modeling-and-relationships/11-1-3-the-shopcore-schema) plus the `schema_migrations` ledger from [12.3.1](/book/part-04-databases-backend-and-full-stack-development/12-sql-postgresql-and-mongodb/12-3-postgresql-in-practice/12-3-1-schemas-constraints-and-migrations).

## 5. Conventions Used Throughout

- **JavaScript (ES Modules), not TypeScript** — production pragmatism for a book you finish; types appear via JSDoc where valuable. Swap to `tsx` + strict TS anytime.
- **Money is integer cents.** Never floats. Display formats `$1,290.00`.
- **IDs are `BIGINT`.** Never strings-as-ids.
- **Every write is Zod-validated.** Every query parameterized.
- **Timestamps are `TIMESTAMPTZ`.** No naive Dates crossing the wire without ISO strings.
- **One source of truth:** `db/migrations/` — never pgAdmin "just edit" in dev and forget.
