Three tools separate MongoDB toy apps from production ones: **compound indexes** (and the ESR rule), the **aggregation pipeline** (MongoDB's SQL GROUP BY, JOINs and transforms in one), and **`$jsonSchema` validation** (schema enforcement inside a "schemaless" database).

## 1. Aggregation Pipelines — Think in Stages, Not Tables

An aggregation is an ordered list of stages. Every stage transforms the document stream handed to the next:

```javascript
db.orders.aggregate([
  { $match:  { status: "paid" } },              // 1. filter (uses index)
  { $unwind: "$items" },                        // 2. one doc per line item
  { $group:  {                                  // 3. collapse per user
      _id: "$userId",
      totalCents: { $sum: { $multiply: ["$items.qty", "$items.unitPriceCents"] } },
      lineItems:  { $sum: 1 },
  } },
  { $sort:   { totalCents: -1 } },              // 4. order output
]);
```

Run it in mongosh against your `shopcore_docs` data — you should see per-user paid totals (`ada@example.com`, etc.). In Compass, the **Aggregations** tab lets you build this visually: **Add Stage → $match → Run**, then add `$unwind`, `$group`, `$sort` one at a time, watching documents transform at each step — the fastest way to learn pipelines.

Key stages — know these cold:

| Stage | Purpose | SQL equivalent |
| :-- | :-- | :-- |
| `$match` | Filter documents early (always first!) | `WHERE` |
| `$project` | Reshape/select fields | `SELECT col, expr AS alias` |
| `$group` | Bucket + aggregate (`$sum`, `$avg`, `$max`, `$addToSet`) | `GROUP BY` |
| `$unwind` | Array → one doc per element | `unnest()` / join lines |
| `$lookup` | Left-join another collection | `LEFT JOIN` |
| `$sort` / `$limit` / `$skip` | Order and page | `ORDER BY` / `LIMIT` |
| `$count` | Count the stream | `COUNT(*)` |
| `$addFields` | Add computed fields | computed `SELECT` columns |

**Rule: put `$match` first.** Every document filtered later costs CPU; unfiltered stages scan everything.

### Real ShopCore question: "Which SKU earned the most?"

```javascript
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $unwind: "$items" },
  { $group: {
      _id: "$items.sku",
      units: { $sum: "$items.qty" },
      revenue: { $sum: { $multiply: ["$items.qty", "$items.unitPriceCents"] } },
  } },
  { $sort: { revenue: -1 } },
]);
```

`KB-01` leads with `12900` (Ada's order). Every number is reproducible from your seed.

## 2. Indexes and the ESR Rule

Mongo indexes work like Postgres B-trees for equality/range/sort, with one famous design rule:

> **ESR — Equality → Sort → Range**: equality fields first, then sort fields, then range fields.

```javascript
// Query: paid orders for one user, newest first
db.orders.find({ userId: "ada@example.com", status: "paid" }).sort({ createdAt: -1 });

// Index following ESR:
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1 });
```

Verify it uses the index (not a collection scan):

```javascript
db.orders.find({ userId: "ada@example.com", status: "paid" })
         .sort({ createdAt: -1 })
         .explain("executionStats");
// Look for: "stage": "IXSCAN" (index scan) — NOT "COLLSCAN"
```

Or in Compass: **Indexes** tab → see all indexes; or **Explain Plan** button → it renders IXSCAN/COLLSCAN visually. Delete indexes you don't need — each costs write performance (`db.orders.dropIndex("userId_1_status_1_createdAt_-1")`).

Compound index column order is **not** cosmetic: an index on `(status, createdAt)` cannot efficiently answer `find({ userId, status })` if `userId` isn't in it.

## 3. `$jsonSchema` — Validation Inside "Schemaless" MongoDB

```javascript
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["userId", "status", "items"],
      properties: {
        userId:    { bsonType: "string" },
        status:    { enum: ["pending", "paid", "shipped", "cancelled"] },
        items: {
          bsonType: "array",
          minItems: 1,
          items: {
            bsonType: "object",
            required: ["sku", "qty", "unitPriceCents"],
            properties: {
              sku:           { bsonType: "string" },
              qty:           { bsonType: "int", minimum: 1 },
              unitPriceCents:{ bsonType: "int", minimum: 0 },
            },
          },
        },
      },
    },
  },
  validationLevel: "moderate",       // only new/updated docs validated; "strict" = everything
  validationAction: "error",         // reject writes (vs "warn")
});

// Prove it works:
db.orders.insertOne({ userId: "x", status: "bogus", items: [] });
// MongoServerError: Document failed validation
```

Find validation on an existing collection: `db.getCollectionInfos({ name: "orders" })` and read its `options.validator`. Update via `db.runCommand({ collMod: "orders", validator: {...} })`.

## 4. Node.js Connection (preview — full code in Ch. 13.2.4)

```javascript
import { MongoClient } from 'mongodb';

const client = new MongoClient(process.env.MONGODB_URI);   // e.g. mongodb://127.0.0.1:27017
await client.connect();
const orders = client.db('shopcore_docs').collection('orders');
const paid = await orders.find({ status: 'paid' }).toArray();
await client.close();   // close on shutdown, not per request — reuse one client
```
