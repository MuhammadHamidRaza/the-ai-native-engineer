Good TypeScript does **not** mean writing redundant type annotations on every single line (`const count: number = 1`). Good TypeScript lets inference do the repetitive work while annotating **function boundaries, data models, and uncertain inputs** cleanly. Subchapter **05.1** teaches how structural typing, unions, and control-flow narrowing catch bugs at compile time.

## Lessons in Subchapter 05.1

1. **[05.1.1 Type Inference and Annotations](/book/part-02-javascript-and-frontend-development/05-typescript-for-professional-development/05-1-static-typing-foundations/05-1-1-type-inference-and-annotations):** When to rely on inference vs. explicit parameter/return types, plus why `unknown` is strictly safer than `any`.
2. **[05.1.2 Interfaces, Type Aliases and Unions](/book/part-02-javascript-and-frontend-development/05-typescript-for-professional-development/05-1-static-typing-foundations/05-1-2-interfaces-type-aliases-and-unions):** Structural typing, `interface` vs `type`, union literals, optional vs `undefined`, and `readonly` data.
3. **[05.1.3 Narrowing and Type Guards](/book/part-02-javascript-and-frontend-development/05-typescript-for-professional-development/05-1-static-typing-foundations/05-1-3-narrowing-and-type-guards):** `typeof`, `Array.isArray`, `in`, `instanceof`, equality narrowing, and custom `is` type predicates.
