Shipping a real React application requires more than local toy counters. Users experience slow networks, failed mutations, empty datasets, sluggish lists, and keyboard-only navigation—and you must verify your builds, tests, and accessibility before deploying.

## Lessons in Subchapter 07.3

1. **[07.3.1 Data Fetching, Caching and Mutations](/book/part-02-javascript-and-frontend-development/07-react-development/07-3-production-react-patterns/07-3-1-data-fetching-caching-and-mutations):** Modeling `loading` / `error` / `empty` / `success` UI states explicitly, mutations with rollback, and why TanStack Query beats hand-rolled `useEffect` fetching at scale.
2. **[07.3.2 Performance Optimization and Memoization](/book/part-02-javascript-and-frontend-development/07-react-development/07-3-production-react-patterns/07-3-2-performance-optimization-and-memoization):** Profiling before optimizing, when `React.memo`/`useMemo`/`useCallback` actually help, running `npm run build` + `npm run preview`, and testing components with **Vitest + React Testing Library**.
3. **[07.3.3 Accessible UI Component Libraries](/book/part-02-javascript-and-frontend-development/07-react-development/07-3-production-react-patterns/07-3-3-accessible-ui-component-libraries):** Choosing headless primitives (Radix UI / React Aria) vs. custom HTML/CSS, and knowing when you do *not* need an extra library.
