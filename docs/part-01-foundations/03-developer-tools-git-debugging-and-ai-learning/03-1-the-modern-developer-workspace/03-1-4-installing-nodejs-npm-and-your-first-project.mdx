`03.1.3` taught you that `package.json` is a dependency contract and that lockfiles make installs reproducible. That contract is only useful if the tool that reads it — the **Node.js runtime** and the **npm CLI** — is installed, on your `PATH`, and pinned to a version your project can actually run. Chapters 04–08 assume a working Node.js toolchain; this lesson installs it once, correctly, and proves it with a running project before you write your first line of JavaScript.

## 1. What Node.js Is — and What It Is Not

**Node.js** is a runtime that executes JavaScript *outside* the browser, directly on your operating system, built on Google's open-source **V8** engine. The same language you will use for frontend UI (`React`) also runs servers (`Part 04`), build pipelines, test runners, CLI tools, and AI-agent scripts — one language, one mental model, two worlds.

- **Node.js is not a programming language.** JavaScript is the language; Node.js is one environment that runs it.
- **Node.js is not a package manager.** `npm` (Node Package Manager) ships *with* Node.js and installs third-party libraries from [npmjs.com](https://www.npmjs.com).
- **Node.js is not a framework.** Express, Next.js, and Vite are frameworks/libraries you add *on top of* Node.js.

Every command in this book that starts with `node`, `npm`, or `npx` requires a working Node.js installation. Verify now:

```bash
node --version
npm --version
```

If `node` prints something like `v24.22.3` and `npm` prints `11.x.y`, you already have a working install — read on anyway, because version pinning matters.

## 2. LTS vs. Current — Which One Do You Install?

Node.js ships two release lines on a fixed schedule:

| Line | What It Means | Supported Until | Recommendation |
| :--- | :--- | :--- | :--- |
| **LTS** (Long-Term Support, even major numbers: 20, 22, 24…) | Battle-tested, maintenance-only changes | ~3 years per LTS | **Install this** |
| **Current** (odd majors) | Latest features, pre-LTS | Until next release | Only if you need a specific new API |

LTS exists because a runtime you deploy your career on should change slowly and predictably. The exact LTS number in this book (`v26.x` is the newest LTS line as of November 2026, with `v24.x` and `v22.x` still in LTS — verify current status at [nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases), since release lines move) is not critical — what matters is: an **even-numbered LTS release**, installed via a **version manager** so you can switch per project.

## 3. Why a Version Manager Instead of a Direct Install

Installing Node.js directly from its installer works — until two projects need two different Node versions, or a project needs a newer one than the OS ships. **Version managers** let you keep multiple Node versions side by side and switch per directory. The book uses **`nvm`** (Node Version Manager) because its commands are identical across macOS and Linux (and inside Windows' WSL2 Ubuntu), which keeps every later command copy-paste identical for every reader of this book.

| Platform | Recommended Path | Why |
| :--- | :--- | :--- |
| **Windows 11** | **WSL2 Ubuntu** + `nvm` | Every Part 01–10 command runs identically to macOS/Linux inside WSL2 |
| **Windows 11 (native, no WSL)** | `fnm` (Fast Node Manager) | Native Windows port; same mental model as `nvm` |
| **macOS** | `nvm` (install script) or `brew install nvm` | Standard on both Intel and Apple Silicon |
| **Linux (Ubuntu/Debian)** | `nvm` (install script) | Distro-shipped Node is often years out of date |

## 4. Installation — Follow Your Platform Path

### 4.1 Windows 11 (WSL2 Ubuntu — recommended)

You need WSL2 Ubuntu installed first (`00.11.2`). Inside the WSL terminal:

```bash
# 1. Install nvm (official install script from github.com/nvm-sh/nvm)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash

# 2. Reload your shell configuration so `nvm` becomes available
source ~/.bashrc   # or ~/.zshrc if you use zsh

# 3. Install the active LTS line and make it default
nvm install --lts
nvm alias default 'lts/*'

# 4. Verify
node --version
npm --version
```

> **Security note on `curl | bash`:** piping a script from the network straight into a shell executes whatever that URL serves right now. This is the *officially documented* nvm install path (source: the nvm project's README), but treat it with the respect you would any remote script: read the URL (`raw.githubusercontent.com/nvm-sh/nvm` — the official repository), pin a version tag (`v0.41.0`), and never run it with `sudo`. A version tag is not a guarantee, it is a reproducibility convenience.

### 4.2 Windows 11 (native, no WSL) — `fnm`

In **PowerShell** (not WSL):

```powershell
# Requires winget (built into Windows 11)
winget install Schniz.fnm

# Enable fnm in your shell (one-time)
fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression

# Persist it for future sessions
Add-Content -Path $PROFILE -Value 'fnm env --use-on-cd --shell powershell | Out-String | Invoke-Expression'

# Install LTS and verify
fnm use --install-if-missing lts-latest
node --version
npm --version
```

### 4.3 macOS

```bash
# Option A: official install script (same as Linux/WSL)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash
source ~/.zshrc
nvm install --lts

# Option B: Homebrew
brew install nvm
mkdir -p ~/.nvm
# Then add the nvm initialization snippet printed by `brew info nvm` to ~/.zshrc
nvm install --lts

node --version && npm --version
```

### 4.4 Linux (Ubuntu 22.04 / 24.04+)

```bash
sudo apt update
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.41.0/install.sh | bash
source ~/.bashrc
nvm install --lts
node --version && npm --version
```

> **Do not** `sudo npm install` packages, and do not install Node.js into a system path you cannot manage without root. If a command in this book ever requires `sudo` for `npm`, stop and re-read the instruction instead.

## 5. Your First Node Project — 10 Minutes, Fully Verified

```bash
mkdir -p ~/code/ai-native-engineer/hello-node && cd ~/code/ai-native-engineer/hello-node
npm init -y
```

`npm init -y` writes `package.json` with sensible defaults. Open it:

```json
{
  "name": "hello-node",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  }
}
```

Two details matter:

- **`main`** is the entry point for `require('hello-node')` consumers.
- **`scripts`** registers named commands runnable via `npm run <name>`. We will add a real one now.

Create `index.js`:

```js
// index.js — your first executed Node program
const args = process.argv.slice(2);
const name = args[0] ?? 'engineer';

console.log(`Hello, ${name}. Node ${process.version} is ready.`);
console.log(`Running on: ${process.platform} (${process.arch})`);
```

Run it directly and through an npm script:

```bash
node index.js Hamid
# Hello, Hamid. Node v26.13.1 is ready.
# Running on: linux (x64)

# Add a start script
npm pkg set scripts.start="node index.js"
npm run start -- Hamid
```

```text
> hello-node@1.0.0 start
> node index.js Hamid

Hello, Hamid. Node v26.13.1 is ready.
```

Now add one dependency and see how `npm` behaves:

```bash
npm install chalk@5
cat index.js >/dev/null  # sanity check the file is still there
node --version
npm ls --depth=0
# hello-node@1.0.0 /home/you/code/ai-native-engineer/hello-node
# └── chalk@5.x.y
```

Three things just appeared in your project folder, and each one has a job:

| Artifact | Job | Committed to Git? |
| :--- | :--- | :---: |
| `package.json` | Dependency contract: names + version *ranges* | **Yes** |
| `package-lock.json` | Exact resolved versions + integrity hashes | **Yes** |
| `node_modules/` | The actual unpacked libraries | **Never** (`.gitignore`) |

`node_modules/` is a build artifact. Given `package.json` + `package-lock.json`, anyone (including CI and your teammates) reproduces your exact environment with `npm ci`.

## 6. `npm ci` vs. `npm install` — The One Rule That Matters

- `npm install` — resolves semver ranges, **may update** `package-lock.json`. Use when adding/changing dependencies.
- `npm ci` — installs exactly what the lockfile says, deletes `node_modules/` first, **never** modifies the lockfile. Use in CI and whenever reproducing an environment.

If `npm ci` fails with a lockfile mismatch error, your `package.json` and `package-lock.json` disagree — fix the manifest, don't bypass with `--force`.

## 7. PATH Troubleshooting — "command not found" After Installing

| Symptom | Cause | Fix |
| :--- | :--- | :--- |
| `node: command not found` | Shell hasn't reloaded, or `nvm` init lines missing | `source ~/.bashrc` (or `~/.zshrc`); verify `nvm` init lines exist at the bottom |
| `nvm: command not found` | Install script wrote to a different shell profile | Check `~/.bashrc`, `~/.zshrc`, `~/.profile`; rerun `source` |
| `npm` resolves to a *different* Node than `nvm use` selected | Conflicting global Node earlier in `PATH` | `which -a node` / `where.exe node`; remove the older install or reorder PATH |
| Global packages (`npm i -g`) land in permission errors | `sudo` used with npm | Never use `sudo` with npm; with `nvm`, globals live in `~/.nvm/...` and need no sudo |
| WSL `nvm` works but Windows `node` also exists and shadows it | Invoking from the wrong shell | Be explicit: run Node commands inside WSL, or use `fnm` on Windows native — never mix both for the same project |

Diagnostic one-liners worth memorizing:

```bash
which -a node        # every node on PATH, in order
echo "$PATH" | tr ':' '\n'   # PATH, one entry per line
nvm current          # which Node nvm thinks is active here
```

## 8. Version Conflicts — Pinning Per Project with `.nvmrc`

Create `.nvmrc` in the project root containing the version you developed against:

```bash
echo "lts/*" > .nvmrc   # latest LTS — or pin a specific version, e.g. "24" (never literal "--lts", which nvm cannot parse)
```

Then `nvm use` in that directory switches automatically (or reads `.nvmrc` on `cd` with nvm's bash hook). Commit `.nvmrc`; teammates with `nvm` get the right Node with one command.

## 9. Cleanup

```bash
cd ~/code/ai-native-engineer
rm -rf hello-node    # only the scratch project; nothing else references it
```

Nothing else was installed globally. `nvm` remains — keep it.

## 10. Acceptance Criteria

You are done when all of these hold:

- [ ] `node --version` prints an **even-numbered LTS** (`v22.x`, `v24.x`, `v26.x`…).
- [ ] `npm --version` prints a working npm.
- [ ] `npm init -y` produced a `package.json` in a fresh `~/code/ai-native-engineer/hello-node`.
- [ ] `node index.js YourName` printed your name and the Node version.
- [ ] `npm run start -- YourName` did the same via npm scripts.
- [ ] `.gitignore` exists and excludes `node_modules/` (add `node_modules/` if missing).
- [ ] `npm ls --depth=0` lists your one dependency (`chalk`), nothing global.

## Common Mistakes

1. **Installing a random pre-LTS "Current" Node** because a blog post said so — pin LTS; upgrade deliberately, not accidentally.
2. **Running `npm install` as root/sudo** — corrupts ownership of `~/.nvm` and system paths; always fix the underlying PATH/permissions issue instead.
3. **Committing `node_modules/`** — hundreds of MB, machine-specific paths, zero benefit; commit the lockfile instead.
4. **Mixing package managers** — if the repo has `package-lock.json`, use `npm`; don't add `yarn.lock` or `pnpm-lock.yaml`.
