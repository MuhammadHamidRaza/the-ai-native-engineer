## 0. Read Before Touching Anything — Budget & Scope

**Path A (required, $0):** two local clusters — **kind** (`shopcore-a`, upstream Kubernetes in Docker) and **k3d** (`shopcore-b`, k3s in Docker: a genuinely different distribution and runtime). No cloud account, no cost. This is your multi-cloud rehearsal.

**Path B (optional, real second cloud, GATED on billing alert):** one managed/VM Kubernetes on a second cloud (Oracle Always Free ARM VM + k3s, or GKE within the free-tier credit). **Set a budget alert BEFORE creating anything.** EKS has **no** free control plane ($0.10/cluster/hr ≈ $73/mo — skip it for this lab). Teardown steps below are **mandatory**, not optional.

## 1. Path A — Build Once, Deploy Twice

Where to run: WSL2/Linux shell with Docker, kind, k3d, kubectl and Helm from 20.1.

```bash
# install k3d (single binary): pick ONE
curl -s https://raw.githubusercontent.com/k3d-io/k3d/main/install.sh | bash
# or: winget install k3d-io.k3d  /  brew install k3d

kind create cluster --name shopcore-a
k3d cluster create shopcore-b --port "8081:80@loadbalancer"
kind load docker-image shopcore-api:1.0.0 --name shopcore-a
k3d image import shopcore-api:1.0.0 --cluster shopcore-b
kubectl get nodes --context kind-shopcore-a
kubectl get nodes --context k3d-shopcore-b
```

Expected: `shopcore-a-control-plane Ready` and `k3d-shopcore-b-server-0 Ready` (note k3d nodes are servers/agents, k3s runs both roles).

**One manifest, both clusters** (`shopcore-api.yaml` — identical file applied twice):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: shopcore-api, namespace: shopcore }
spec:
  replicas: 2
  selector: { matchLabels: { app: shopcore-api } }
  template:
    metadata: { labels: { app: shopcore-api } }
    spec:
      containers:
        - name: api
          image: shopcore-api:1.0.0
          imagePullPolicy: IfNotPresent
          ports: [{ containerPort: 4000 }]
          readinessProbe: { httpGet: { path: /health, port: 4000 } }
---
apiVersion: v1
kind: Service
metadata: { name: shopcore-api, namespace: shopcore }
spec:
  selector: { app: shopcore-api }
  ports: [{ port: 80, targetPort: 4000 }]
```

```bash
kubectl --context kind-shopcore-a apply -f shopcore-api.yaml -n shopcore --create-namespace
kubectl --context k3d-shopcore-b apply -f shopcore-api.yaml -n shopcore --create-namespace
kubectl --context kind-shopcore-a rollout status deployment/shopcore-api -n shopcore
kubectl --context k3d-shopcore-b rollout status deployment/shopcore-api -n shopcore
```

**Ingress — same config, one honest caveat.** k3s bundles Traefik, so the identical Ingress works out of the box there:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shopcore, namespace: shopcore }
spec:
  ingressClassName: traefik
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: shopcore-api, port: { number: 80 } }
```

```bash
kubectl --context k3d-shopcore-b apply -f ingress.yaml
curl -i http://localhost:8081/health          # straight through k3d's loadbalancer → Traefik → pods
kubectl --context kind-shopcore-a port-forward -n shopcore svc/shopcore-api 8080:80 &
curl -i http://localhost:8080/health          # kind side (port-forward; or install Traefik via helm for identical Ingress)
```

Expected: HTTP 200 from **both**. The caveat to internalize: the Ingress *resource* is portable; the **controller and ingressClassName are not** — Traefik (k3s default) vs kind's native ingress (cloud-provider-kind) vs cloud controllers each own the data plane. That portability boundary is exactly what 20.3.1's scorecard predicted.

**Compare latency** (honest loopback comparison — measures variance and overhead, not geography):

```bash
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "kind: %{time_total}s\n" http://localhost:8080/health
  curl -s -o /dev/null -w "k3s:  %{time_total}s\n" http://localhost:8081/health
done
```

Both will be milliseconds. Record them anyway — the habit (measuring, comparing, writing it down) is the deliverable.

## 2. Path B (Optional) — The Same on a Real Second Cloud

Only after a budget alert exists. Recommended, $0: **Oracle Always Free ARM VM** (shape `VM.Standard.A1.Flex`, e.g., 2 OCPU / 12 GB — free forever if you stay in Always Free shapes), then:

```bash
ssh ubuntu@<vm-public-ip>
curl -sfL https://get.k3s.io | sh -           # single-node k3s, real cloud VM
sudo kubectl get nodes
# build image locally, export, import remotely:
docker save shopcore-api:1.0.0 | ssh ubuntu@<vm-public-ip> 'docker load'
kubectl apply -f shopcore-api.yaml --server=https://<vm-public-ip>:6443 --insecure-skip-tls-verify=true   # throwaway VM only; never point --insecure at a cluster you care about
```

Alternative $0-ish: **GKE** zonal cluster — free-tier credit covers the management fee; nodes are tiny; still set a $10 budget alert. **Do not** run EKS for this. Full teardown (mandatory): delete the Deployment/Services/Ingress, then **terminate the VM / delete the cluster**, verify the bill shows $0 new spend, and delete the kubeconfig context.

## 4. Mandatory Teardown — Last Step, Not Optional

```bash
kubectl --context kind-shopcore-a delete ns shopcore
kubectl --context k3d-shopcore-b delete ns shopcore
kind delete cluster --name shopcore-a
k3d cluster delete shopcore-b
kind get clusters && k3d cluster list     # must both report empty/none
# cloud path only: terminate VM / delete cluster in the console; confirm $0 in billing;
# remove the cloud kubeconfig context; confirm no stray disks/IPs remain.
```

A lab you didn't tear down is a bill, not an exercise.

## 5. Troubleshooting

| Symptom | Likely cause | Fix |
| :-- | :-- | :-- |
| k3d cluster create hangs at port 8081 | Port already bound | Use `--port "8091:80@loadbalancer"` and curl 8091 |
| Pods `ImagePullBackOff` on k3d | `k3d image import` skipped | Re-import; k3d nodes can't see your host image store |
| `8081` connection refused | Loadbalancer mapping wrong / k3d proxy down | `k3d cluster stop shopcore-b` then start; verify `docker ps` shows k3d proxy |
| kind context missing | kubeconfig merge issue | `kind export kubeconfig --name shopcore-a` |
| curl via cloud VM times out | k3s Traefik only on vm IP; 6443 vs 80 confusion | Security list must allow 80/443 to the VM; test from your laptop |
| Both clusters show same pods? | Context confusion | Always pass `--context`; add `kubectl config current-context` sanity check to your muscle memory |
