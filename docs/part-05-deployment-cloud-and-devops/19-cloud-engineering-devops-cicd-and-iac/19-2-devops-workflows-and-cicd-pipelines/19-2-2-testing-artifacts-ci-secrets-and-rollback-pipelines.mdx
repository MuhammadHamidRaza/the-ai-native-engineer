A green lint is necessary but not sufficient. This lesson adds the real gates: a test job that must pass before anything ships, build artifacts you can download, cloud credentials that are never passwords (AWS OIDC), and a deploy job that can redeploy the previous SHA — the difference between "we rolled back in 2 minutes" and "we are down until someone fixes it."

## 1. The Full Pipeline Shape

```yaml
name: ci-cd
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test -- --ci
      - uses: actions/upload-artifact@v4
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        with:
          name: shopcore-api-dist
          path: dist/
          retention-days: 14

  deploy:
    needs: test                      # only runs if test is green
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write                # required for OIDC
      contents: read
    environment: production           # enables protection rules / required reviewers
    steps:
      - uses: actions/checkout@v7
      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v6.3.0
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: us-east-1
      - name: Deploy
        run: echo "deploy ${{ github.sha }} (see rollback below)"
```

**Where to run:** committed to `.github/workflows/`; executes on GitHub's runners. The upload-artifact pin (`@v4`) is the taught major — as of Nov 2026 v7 exists; identical usage. The AWS credentials action is pinned to the verified current release `aws-actions/configure-aws-credentials@v6.3.0` (Nov 2026); majors older than v5 target deprecated Node runtimes, so don't copy `@v1`-`@v4` snippets from old blog posts.

## 2. Secrets — and Why OIDC Beats Them

GitHub gives you three tiers, all injected as env vars at runtime — never printed, masked in logs:

1. **Repository secrets** — Settings → Secrets and variables → Actions → New repository secret. Use for things that have no better option (e.g., `SLACK_WEBHOOK_URL`).
2. **`GITHUB_TOKEN`** — automatic per-run token; scope it per job with `permissions:` (read-only by default on new repos). Use it for anything GitHub-native: tags, comments, releases, artifacts.
3. **OIDC federation (the right answer for cloud)** — GitHub presents a short-lived, cryptographically signed identity token; AWS (or Azure/GCP) validates it against a trust policy and hands back **temporary** credentials. **No long-lived AWS access keys stored anywhere.**

OIDC setup sketch (AWS): create an IAM OIDC identity provider for `token.actions.githubusercontent.com`; create a role whose trust policy allows `repo:OWNER/REPO:ref:refs/heads/main` (note the repo+ref restriction — this is what stops a fork/branch from assuming production); attach least-privilege permissions (e.g., ECR push or ECS deploy — nothing more); store the role ARN in `vars.AWS_DEPLOY_ROLE_ARN` (a *variable*, not a secret — ARNs aren't credentials). Full walkthrough: [docs.github.com OIDC](https://docs.github.com/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect).

**Never** put AWS access keys, DB passwords, or `.env` contents in workflow YAML, logs, artifact uploads, or Slack messages. Forked PRs don't receive repo secrets at all — by design.

## 3. Hardening the Workflow Itself — Permissions, Concurrency, Environments

**Minimal `permissions:`, always explicit.** The default `GITHUB_TOKEN` is broad on older repos; scope it:

```yaml
permissions:
  contents: read        # this job checks out code and nothing else
```

The deploy job needs more (the OIDC token), so only *that* job gets `id-token: write`. Read access is the floor everywhere else.

**Cancel superseded runs** so a rapid push storm doesn't burn minutes on stale commits:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

**Environment protection:** the `environment: production` line in the deploy job does two things — (a) it gates the job behind protection rules (required reviewers, wait timer, allowed branches) set under Settings → Environments, and (b) it scopes environment-level secrets to that job only. For a solo learning repo you can skip the reviewer gate; for anything client-facing, one approving eyeball before deploy is the cheapest insurance you will ever buy.

**Supply-chain hygiene:** prefer actions from verified creators; pin to major tags (`@v4`) at minimum and consider SHA-pinning (`uses: actions/checkout@<sha> # v4.x`) for production deploy workflows; enable Dependabot for `github-actions` ecosystem so version bumps arrive as PRs.

**`GITHUB_TOKEN` permissions cheat sheet:**

| Permission | Grants | Typical use here |
| :-- | :-- | :-- |
| `contents: read` | Checkout the repo | Default posture — 19.2.1 uses only this |
| `id-token: write` | Present the OIDC identity to AWS | Deploy job only |
| `pull-requests: write` | Comment on PRs | Labeler/bot workflows — not this pipeline |
| `packages: write` | Push to GHCR | Only if pushing images there |
| `issues: write` | Open/comment issues | Optional auto-issue on failure |

Rule: enumerate only the permissions your steps use; anything unlisted stays denied. Audit with `gh auth status` and the run's token summary.

## 4. Artifacts — What They Are For

`actions/upload-artifact` stores build outputs (`dist/`, coverage reports) attached to the workflow run, downloadable from the UI or `gh run download <id>`. Uses: prove the exact bytes that would ship, share with QA, feed downstream jobs with `download-artifact`. Retention is configurable (`retention-days`) — storage counts toward repo quota on private repos, so 14 days is a sane default; don't archive `node_modules`.

## 5. Rollback — Redeploy the Previous SHA

Every merge has `github.sha`. A production incident means: identify the last-known-good SHA (`git log --oneline main`), then one of:

```bash
# Option A — revert the bad merge (preferred: history stays honest)
git revert <bad-sha>
git push origin main            # pipeline redeploys the reverted state

# Option B — redeploy previous artifact from the run (no revert needed)
gh run download <last-good-run-id> --name shopcore-api-dist
```

Codify Option A: a `workflow_dispatch` input `rollback_to_sha` that checks out that SHA and runs the deploy job — a button labeled "Rollback to input SHA" beats archaeology at 2 a.m. Practice Option B once so you trust it.

**Notifications on failure:** the deploy job gets `if: failure()` as a final step — e.g., `curl -X POST "$SLACK_WEBHOOK_URL" -d '{"text":"ShopCore deploy FAILED — $GITHUB_SHA"}'` — plus GitHub's built-in email notifications (Settings → Notifications). Test the webhook path by forcing a failing step once: a broken alert channel is worse than none.

| Channel | Setup | Best for | Noise |
| :-- | :-- | :-- | :-- |
| GitHub email | On by default for watching repos | Solo devs | High volume |
| Slack/Teams webhook | `curl` step, secret `SLACK_WEBHOOK_URL` | Team visibility | Medium |
| PagerDuty / Opsgenie | Only on prod deploy failure | On-call escalation | Low, but wakes people |
| Status page (Statuspage) | Separate tool | Customer comms | Public |

Rule: notify on **deploy failure only** on prod; log everything else. Alert fatigue is real — the third ignored 3 a.m. ping is when the one that matters gets missed.

**Close the loop from CI to production:** after `docker compose up -d` on the server (via SSH, Ansible from 19.3.2, or a provider action), the pipeline should `curl` the health endpoint and fail loudly if it doesn't return 200 within ~30 s — a green workflow attached to a dead service is lying to you.

## 6. Troubleshooting the Classics

| Symptom | Likely cause | Fix |
| :-- | :-- | :-- |
| Deploy job skipped | `needs: test` failed, or `if:` branch mismatch | Check the skipped-job tooltip; verify ref condition |
| OIDC step: "Not authorized to perform sts:AssumeRoleWithWebIdentity" | Trust policy repo/ref mismatch | Match `repo:OWNER/REPO:ref:refs/heads/main` exactly; check `permissions: id-token: write` |
| Artifact download empty | Wrong `path:` or upload ran after a changed dir | Verify path locally; `ls` before upload in a debug step |
| Secret shows as `***` but app still fails auth | Secret has trailing newline / wrong value | Re-set via `gh secret set NAME` from a file without trailing newline |
| Rollback didn't roll back | Deploy job can't checkout arbitrary SHA | Use `actions/checkout@v7` with `ref: ${{ inputs.rollback_to_sha }}` |
| Fork PR can't deploy | By design — forks get no secrets/OIDC | Deploy only from `main` in the base repo |

## 7. Practice

**Guided.** Add the `test` job and artifact upload to your CI; push; confirm the artifact appears on the run page and downloads.

**Independent.** Configure AWS OIDC for a test role (or, without AWS: a `workflow_dispatch` echo deploy). Deliberately fail a deploy validation step and confirm your failure notification fires.

**Challenge.** Add `workflow_dispatch` input `rollback_to_sha`; implement the rollback path; rehearse it: deploy SHA A → deploy SHA B → roll back to A → verify served version.

**Assessment checklist**

- [ ] My deploy job cannot start unless tests passed (`needs: test`).
- [ ] I upload the built artifact and can download it from the run.
- [ ] I use `GITHUB_TOKEN` for GitHub-native actions and OIDC for AWS — no stored passwords.
- [ ] I can articulate what the OIDC trust policy restricts (repo, ref) and why.
- [ ] I have a rehearsed rollback to a previous SHA with a notification attached.
- [ ] If notifications fire, I know exactly where they go and who acts.
